## Introduction

This lab, **Feature Store Concepts**, builds the smallest possible feature store from scratch so you can see the three ideas that every production feature store is made of: the offline/online store split, point-in-time correctness (PITC), and feature freshness. You will write the leaky query that breaks a fraud model, fix it with one SQL clause, then copy the latest snapshot from a slow PostgreSQL database into a fast Redis database and read it back in under a millisecond.

Imagine you bake cookies (your ML model) and you need flour (your features). You have two problems. When you are testing recipes (training), you want a big pantry with months of flour shipments so you can study how each batch affected past cookies. When a customer walks in (serving), you want that customer's flour ready in 1 second, not 1 minute. A feature store is the pantry plus the grab-bag: two databases with two very different jobs, and one rule that keeps your training honest.

![Feast feature store architecture](https://github.com/tajuar-akash-hub/Labs/blob/main/Feature_store_labs/animation/7.1_main_feature-lab-architecture.svg)

The offline store is PostgreSQL: big, slow, holds full history, and is what you query when training a model. The online store is Redis: small, fast, holds only the latest snapshot per entity, and is what you query when serving a prediction. The bridge between them is a materialization job that copies the newest rows across. The rule that keeps training honest is point-in-time correctness: at training time, you may only use feature values that were already true on or before the label's timestamp. Break that rule and your offline metrics look amazing while your production model quietly falls apart.



### Key focus: the whiteboard sketch

The three ideas above are what you are supposed to be able to sketch on a whiteboard after this lab. Keep this picture in mind as you build each step.

Three ideas the picture captures, which is the entire lab in one diagram:

1. **Two stores.** On the left is history (PostgreSQL). On the right is the latest snapshot (Redis). They have different jobs and different performance characteristics.
2. **One bridge.** The materialize arrow copies the newest row per entity from left to right. Without it, the online store goes stale and your serving predictions get worse silently.
3. **One rule.** The PITC filter only lets feature rows from before the label's timestamp through. That single clause is what stops leakage.

## Prologue

You trained a fraud model. It looked great. Six months later it started getting worse. Why?

During training, you joined "the latest user info" with "fraud labels from five days ago". The problem is that "latest user info" included things that happened *after* the fraud. Your model learned from the future: it learned that users who look like this get flagged as fraud, without realizing those features were only collected *because* of the fraud.

This is **feature leakage**. It makes your offline metrics look amazing and your production model look terrible. A feature store with point-in-time joins prevents it. In this lab you will reproduce the bug, then fix it, then build the fast serving path on top of the corrected data.

### Step 5: Create `init_schema.sql` with the two tables

> Note: this step defines the two tables the whole lab depends on: one for feature values over time, one for the labels we want to predict.

Create a new file called `init_schema.sql` in `~/poridhi-lab-7-1/feature_repo` and paste the SQL below into it.

```sql
-- One row per (entity, feature, day). This is the offline store's history table.
CREATE TABLE IF NOT EXISTS feature_values (
    entity_id       TEXT              NOT NULL,   -- the entity, for example 'alice'
    feature_name    TEXT              NOT NULL,   -- the feature, for example 'tx_count_7d'
    feature_value   DOUBLE PRECISION NOT NULL,   -- the number
    event_timestamp TIMESTAMPTZ       NOT NULL,   -- WHEN this value was true
    PRIMARY KEY (entity_id, feature_name, event_timestamp)
);

-- One row per (entity, day) for the answer the model is trying to predict.
CREATE TABLE IF NOT EXISTS labels (
    entity_id       TEXT        NOT NULL,
    label           INT         NOT NULL,          -- 0 or 1, where 1 means fraud
    event_timestamp TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (entity_id, event_timestamp)
);
```

> Would I get an error if I ran this? No. The `IF NOT EXISTS` clauses make it safe to run more than once, which matters because the lab VM may already have these tables from an earlier attempt.

### Step 7: Seed a small amount of fake data

Create a new file called `seed.py` in `~/poridhi-lab-7-1/feature_repo` and paste the Python below into it.

```python
# seed.py: fill the offline store with a tiny bit of fake data.
import random
from datetime import datetime, timedelta, timezone

import psycopg2

from common import pg_dsn

now = datetime.now(timezone.utc)          # current time in UTC
conn = psycopg2.connect(**pg_dsn())
cur = conn.cursor()

entities = ["alice", "bob", "carol"]     # three fake entities

rows = []
for e in entities:
    for d in range(5):                   # 5 days of history
        ts = now - timedelta(days=4 - d)  # walks back 4, 3, 2, 1, 0 days
        rows.append((e, "tx_count_7d", random.randint(1, 20), ts))
        rows.append((e, "avg_tx_amount", round(random.uniform(10, 100), 2), ts))

# ON CONFLICT DO NOTHING means re-running this script is harmless.
cur.executemany(
    "INSERT INTO feature_values VALUES (%s,%s,%s,%s) ON CONFLICT DO NOTHING",
    rows,
)

# One label per entity, dated two days ago: the "fraud happened on day X" we predict.
labels = [(e, random.randint(0, 1), now - timedelta(days=2)) for e in entities]
cur.executemany(
    "INSERT INTO labels VALUES (%s,%s,%s) ON CONFLICT DO NOTHING",
    labels,
)

conn.commit()
print(f"Inserted {len(rows)} feature rows and {len(labels)} labels.")
conn.close()
```

### Step 8: Run the leaky query, the bug

> Note: this step writes the query that looks correct but is broken, so you can see feature leakage in the output with your own data.

Create a new file called `leaky.py` in `~/poridhi-lab-7-1/feature_repo` and paste the Python below into it.

```python
# leaky.py: THIS IS THE BUG. Do not write training queries like this.
import psycopg2

from common import pg_dsn

conn = psycopg2.connect(**pg_dsn())
cur = conn.cursor()

# For each label we join the LATEST feature values for that entity.
# "Latest" means "newest in the table", which can be AFTER the label's
# timestamp. That is leakage.
cur.execute(
    """
    SELECT l.entity_id,
           l.event_timestamp AS label_ts,   -- when the fraud (or not) happened
           f.event_timestamp AS feat_ts,    -- when the feature was true
           f.feature_name, f.feature_value
    FROM labels l
    JOIN LATERAL (
        SELECT feature_name, feature_value, event_timestamp
        FROM feature_values
        WHERE entity_id = l.entity_id
        ORDER BY event_timestamp DESC      -- newest first
        LIMIT 2                            -- just two features
    ) f ON TRUE
    ORDER BY l.entity_id, f.feature_name;
    """
)

rows = cur.fetchall()
for entity_id, label_ts, feat_ts, name, value in rows:
    flag = "LEAK" if feat_ts > label_ts else "ok"
    print(f"{entity_id:6s} label_ts={label_ts:%Y-%m-%d} feat_ts={feat_ts:%Y-%m-%d} "
          f"{name:15s} value={value:8.2f}  {flag}")

leaked = sum(1 for _, label_ts, feat_ts, _, _ in rows if feat_ts > label_ts)
print(f"\n{leaked} of {len(rows)} joined rows leak future information.")
conn.close()
```

Run it:

```bash
python leaky.py
```

![leaky.py, 6 of 6 leaking](https://github.com/tajuar-akash-hub/Labs/blob/main/Feature_store_labs/images/7.1_leaky_query_demo.png)

> Would I get an error if I ran this? No. The query is valid SQL; the bug is semantic, not syntactic, which is exactly what makes leakage dangerous in real projects. If you see `0 of 6 joined rows leak`, check that Step 7 actually committed and that you are reading the output of this script rather than a stale one.

Why it leaks: the label is dated two days ago, but `ORDER BY event_timestamp DESC LIMIT 2` picks the two newest feature rows for that entity, and those rows are from today. The model is being trained on information that did not exist when the label was written.

### Step 9: Fix the leak with a point-in-time join

> Note: this step adds the single clause that makes the join correct, and asserts the fix programmatically instead of leaving you to eyeball dates.

Create a new file called `pitc.py` in `~/poridhi-lab-7-1/feature_repo` and paste the Python below into it.

```python
# pitc.py: the CORRECT version. The only difference from leaky.py is the extra
# WHERE clause: event_timestamp <= l.event_timestamp
import psycopg2

from common import pg_dsn

conn = psycopg2.connect(**pg_dsn())
cur = conn.cursor()

cur.execute(
    """
    SELECT l.entity_id,
           l.event_timestamp AS label_ts,
           f.event_timestamp AS feat_ts,
           f.feature_name, f.feature_value
    FROM labels l
    JOIN LATERAL (
        SELECT feature_name, feature_value, event_timestamp
        FROM feature_values
        WHERE entity_id = l.entity_id
          AND event_timestamp <= l.event_timestamp   -- THE FIX
        ORDER BY event_timestamp DESC
        LIMIT 2
    ) f ON TRUE
    ORDER BY l.entity_id, f.feature_name;
    """
)

rows = cur.fetchall()
for entity_id, label_ts, feat_ts, name, value in rows:
    flag = "LEAK" if feat_ts > label_ts else "ok"
    print(f"{entity_id:6s} label_ts={label_ts:%Y-%m-%d} feat_ts={feat_ts:%Y-%m-%d} "
          f"{name:15s} value={value:8.2f}  {flag}")

leaked = sum(1 for _, label_ts, feat_ts, _, _ in rows if feat_ts > label_ts)
print(f"\n{leaked} of {len(rows)} joined rows leak future information.")

# Fail loudly if the PITC rule is ever broken again.
assert leaked == 0, "PITC violated: a feature row is newer than its label"
print("PITC holds for every row.")
conn.close()
```

Run it:

```bash
python pitc.py
```

![pitc.py, 0 of 6 leaking](https://github.com/tajuar-akash-hub/Labs/blob/main/Feature_store_labs/images/7.1_pitc_fixed_demo.png)

Every `feat_ts` is now on or before `label_ts`. Because both features are selected with a single `ORDER BY event_timestamp DESC LIMIT 2` on the same day of history, they come from the same eligible timestamp: the newest day at or before the label, which is the label's own day. The model can only see information that existed at the time of the event. That is the PITC rule, and it is the entire trick behind correct feature retrieval for training.

> Would I get an error if I ran this? No. If the assertion fires you get `AssertionError: PITC violated`, which means the query was edited without the `<=` clause: restore it and re-run.

### Step 10: Materialize the latest snapshot into the online store

> Note: this step builds the bridge: it copies the newest feature row per (entity, feature) from the offline store into Redis, one hash per entity.

Create a new file called `materialize.py` in `~/poridhi-lab-7-1/feature_repo` and paste the Python below into it.

```python
# materialize.py: copy the LATEST feature value per (entity, feature) into Redis.
import json
from datetime import datetime, timezone

import psycopg2

from common import pg_dsn, redis_client

r = redis_client()
conn = psycopg2.connect(**pg_dsn())
cur = conn.cursor()

# For each (entity, feature) keep only the row with the newest event_timestamp.
cur.execute(
    """
    SELECT entity_id, feature_name, feature_value, event_timestamp
    FROM (
        SELECT entity_id, feature_name, feature_value, event_timestamp,
               ROW_NUMBER() OVER (
                   PARTITION BY entity_id, feature_name
                   ORDER BY event_timestamp DESC
               ) AS rn
        FROM feature_values
    ) t
    WHERE rn = 1;
    """
)

materialized_at = datetime.now(timezone.utc).isoformat()
count = 0
for entity_id, feature_name, feature_value, event_ts in cur.fetchall():
    payload = {
        "value": feature_value,
        "event_timestamp": event_ts.isoformat(),
        "materialized_at": materialized_at,   # when this row entered Redis
    }
    # One Redis hash per entity, one field per feature.
    r.hset(f"features:{entity_id}", feature_name, json.dumps(payload))
    count += 1

print(f"Materialized {count} features into Redis at {materialized_at}.")
conn.close()
```

Run it:

```bash
python materialize.py
```

The count is 6 because there are 3 entities times 2 features. The timestamp printed here is your freshness baseline: it is when the online snapshot was last rebuilt, and Step 11 measures staleness against it.

### Step 11: Read from the online store and measure freshness

> Note: this step is the serving path: it looks up one entity in Redis, times the lookup, and prints the age of each feature against the materialization timestamp.

Create a new file called `online.py` in `~/poridhi-lab-7-1/feature_repo` and paste the Python below into it.

```python
# online.py: what a serving system does: fetch features in under a millisecond.
import json
import time
from datetime import datetime, timezone

from common import redis_client

r = redis_client()

entity_id = "alice"   # try "bob" or "carol" too

t0 = time.perf_counter()
blob = r.hgetall(f"features:{entity_id}")
elapsed_ms = (time.perf_counter() - t0) * 1000

now = datetime.now(timezone.utc)

print(f"\nOnline read for {entity_id}: {elapsed_ms:.2f} ms\n")
for feature_name, raw in blob.items():
    payload = json.loads(raw)
    feat_ts = datetime.fromisoformat(payload["event_timestamp"])
    mat_ts = datetime.fromisoformat(payload["materialized_at"])
    age_h = (now - feat_ts).total_seconds() / 3600

    print(f"  {feature_name:15s} value = {payload['value']}")
    print(f"  {'':15s} feat_ts = {feat_ts:%Y-%m-%d %H:%M:%S}")
    print(f"  {'':15s} mat_ts  = {mat_ts:%Y-%m-%d %H:%M:%S}")
    print(f"  {'':15s} staleness = {age_h:.1f} h old")
    print()
```

Run it:

```bash
python online.py
```

![online.py latency and staleness](https://github.com/tajuar-akash-hub/Labs/blob/main/Feature_store_labs/images/7.1_online_read_freshness.png)

Two things to notice. First, **latency is sub-millisecond**: that is why an online store exists, because the offline store cannot answer a per-request lookup that fast. Second, **freshness**: the gap between `mat_ts` and now is how stale the online snapshot is, and the gap between `feat_ts` and `mat_ts` is how much history the materialization had to catch up on. In this lab both are seconds because you just ran the materialize step. In production the materialization might run hourly, so the online store can be hours behind while the offline store is current. That gap is the single most common cause of a model that worked in training and drifted in production.

> Would I get an error if I ran this? Possibly: `KeyError: 'features:alice'` does not happen here because `hgetall` returns an empty dict, so you would instead see an empty output block. That means Step 10 did not run or materialized a different entity id, so re-run `python materialize.py` first.

## Epilogue

You built the smallest possible feature store: three entities, two features, six Python scripts, one PostgreSQL table pair, and one Redis hash per entity. You reproduced a real training bug, fixed it with a single SQL clause, and proved the fix with an assertion rather than by eyeballing timestamps. You then built the serving path and measured both the latency and the freshness of what it returned.

The bigger picture is that these three ideas scale unchanged. In Feast, Tecton, or any other feature store, the offline store is still the system of record and the only place a correct point-in-time join can happen, the online store is still a derived low-latency projection, and freshness is still the gap between the two. What changes is scale: terabytes instead of thirty rows, thousands of features instead of two, and a materialization pipeline that runs on a schedule instead of by hand.

## Conclusion

This lab built a minimal feature store from managed PostgreSQL and Redis to make three ideas concrete: the offline/online store split, point-in-time correctness, and feature freshness. You reproduced a feature-leakage bug with a query that looked correct, fixed it by adding `event_timestamp <= l.event_timestamp`, then materialized the latest snapshot into Redis and read it back in under a millisecond. The takeaway is that a feature store is not a clever database, it is a split plus a rule: keep history in the offline store, keep a fresh snapshot in the online store, and never let a training query see the future.
